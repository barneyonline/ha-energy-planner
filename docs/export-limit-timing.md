# Export Limit change timing

Energy Planner issues at most one Export Limit setting change per five minutes. This applies to enabling 0 W, disabling the limit, and restoring original watts/slew settings. The existing general command interval can impose a longer wait. There is no tariff-sign exception or additional settings UI.

Before dispatch, Planner persists both its pending command and a reservation for the upstream Enphase control identity (config entry, control unique ID and device). Sensor/Select aliases share that reservation. It survives option edits, resume, integration reload and Home Assistant restart. A stricter interval captured at dispatch remains in force even if the command-rate option is subsequently reduced.

An accepted request is pending until fresh, matching gateway settings readback arrives. Pending or uncertain commands block further writes even after five minutes. Once Planner first observes the matching confirmation, another full 300 seconds must elapse before a subsequent mutation can be issued. For example, a request at 17:00 first observed confirmed at 17:04 cannot be followed by another request before 17:09. Ordinary reads of unchanged settings do not restart this wait.

The upstream API's `last_successful_readback` records a settings read, rather than when the device physically changed. Planner checks that readback is fresh and at least as recent as service dispatch. If a crash leaves only the earlier reservation, recovery requires a new matching read after reconciliation. Its persisted `last_change_observed_at` is the first matching confirmation it observed, rather than a claimed physical-change timestamp. External changes cannot be prevented or reliably attributed through this API; Planner retains its external-change reconciliation and relinquishes superseded baselines. If an intervening external setting retires an uncertain request, a separate 300-second safety wait starts at the first settled observation, without marking the request applied or attributing the external change to Planner. Replayed observations of that request do not extend the wait. A setting already matching before dispatch is a no-op and creates no new confirmation or cooldown.

While deferred, original restoration baselines and pending ownership remain intact. Restoration and explicit resume share the same ceiling. A service rejection retains its dispatch reservation; an uncertain write retains its pending command and cannot be retried through resume. Known unsent requests and genuine no-ops do not consume the change budget. Deferred, skipped and failed requests are not recorded as successful device control or savings.

Planner does not queue tariff commands during the wait. At the earlier of the next tariff boundary or cooldown deadline, a bounded wakeup requests a new plan using current valid forecast intervals and fresh device feedback. If input collection crosses the deadline, Planner queues one immediate fresh replan instead of losing the wakeup. Revisions replace previous intent; a return to the confirmed setting needs no write. Expiry does not override stale/unsupported feedback, invalid identity, pending commands, service availability or other existing execution gates.

During the hold, projected grid export and estimated costs use the fresh, settled confirmed setting: 0 W prevents modeled grid exports, a finite limit caps them, and a disabled limit leaves exports unrestricted. Raw PV production and on-site solar use remain intact. After eligibility, valid tariff intent can inform future projections when timing is the only blocker; pending restoration keeps authority. Pending writes, stale readback and other execution blockers do not establish a confirmed hold or authorize future tariff-control assumptions. These are modelled projections, not measured power or realized savings.

Export Limit diagnostics and next actions expose `export_limit_change_rate_limited`, `next_eligible_change_at`, `last_dispatch_reserved_at` and `last_change_observed_at`. Calendar entries remain planned previews and are labelled deferred while the ceiling applies. The deadline is the earliest timing eligibility, not a promise that other blockers will clear then.

Old records without confirmation timing, present-but-null legacy timestamps and malformed/future timestamps start a conservative, persisted five-minute wait. Backward wall-clock movement similarly re-anchors a bounded wait; it does not silently grant a fresh budget or wait for an accidentally distant future date. Unresolved commands remain blockers independently of clock repair. Repair preserves the original restoration audit identity, so replay after a crash and clock adjustment cannot create another confirmed calendar action for the same request.

Deterministic tests cover these timing and recovery contracts. No live Home Assistant access, physical-device timing validation or deployment is part of this change.
