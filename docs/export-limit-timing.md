# Export Limit change timing

Energy Planner issues at most one Export Limit setting change per five minutes. This applies to enabling 0 W, disabling the limit, and restoring original watts/slew settings. The existing general command interval can impose a longer wait. There is no tariff-sign exception or additional settings UI.

Before dispatch, Planner persists both its pending command and a reservation for the upstream Enphase control identity (config entry, control unique ID and device). Sensor/Select aliases share that reservation. It survives option edits, resume, integration reload and Home Assistant restart. A stricter interval captured at dispatch remains in force even if the command-rate option is subsequently reduced.

An accepted request is pending until fresh, matching gateway settings readback arrives. Pending or uncertain commands block further writes even after five minutes. Once Planner first observes the matching confirmation, another full 300 seconds must elapse before a subsequent mutation can be issued. For example, a request at 17:00 first observed confirmed at 17:04 cannot be followed by another request before 17:09. Ordinary reads of unchanged settings do not restart this wait.

The upstream API's `last_successful_readback` records a settings read, rather than when the device physically changed. Planner checks that readback is fresh and at least as recent as service dispatch. If a crash leaves only the earlier reservation, recovery requires a new matching read after reconciliation. Its persisted `last_change_observed_at` is the first matching confirmation it observed, rather than a claimed physical-change timestamp. External changes cannot be prevented or reliably attributed through this API; Planner retains its external-change reconciliation and relinquishes superseded baselines. If an intervening external setting retires an uncertain request, a separate 300-second safety wait starts at the first settled observation, without marking the request applied or attributing the external change to Planner. Replayed observations of that request do not extend the wait. A setting already matching before dispatch is a no-op and creates no new confirmation or cooldown.

While deferred, original restoration baselines and pending ownership remain intact. Restoration and explicit resume share the same ceiling. A service rejection retains its dispatch reservation. An uncertain write retains its pending command until reconciliation or an operator acknowledges a verified gateway replacement. Known unsent requests and genuine no-ops do not consume the change budget. Deferred, skipped and failed requests are not recorded as successful device control or savings.

Planner does not queue tariff commands during the wait. At the earlier of the next tariff boundary or cooldown deadline, a bounded wakeup requests a new plan using current valid forecast intervals and fresh device feedback. If input collection crosses the deadline, Planner queues one immediate fresh replan instead of losing the wakeup. Revisions replace previous intent; a return to the confirmed setting needs no write. Expiry does not override stale/unsupported feedback, invalid identity, pending commands, service availability or other existing execution gates.

Routine refreshes collect inputs without awaiting Export Limit reconciliation. One background transaction uses the shared command lock and keeps export command readiness closed until its result is durable and still matches current feedback and configuration. The next coalesced refresh can use that result even if telemetry changed the trigger or a newer readback confirmed the same settings. Pending commands and restoration retain their timestamp checks. When a tariff or cooldown wakeup shares a reconciliation already in progress, its next follow-up is queued immediately, including when telemetry coalesces with that request. Startup recovery waits for reconciliation before validating or activating control. Other device actions and owned EV safety stops keep their own checks when command authority is available. Command writes still wait for durable storage and retain their service deadlines. Refresh diagnostics report the background transaction separately from planner input and worker time.

During the hold, projected grid export and estimated costs use the fresh, settled confirmed setting: 0 W prevents modeled grid exports, a finite limit caps them, and a disabled limit leaves exports unrestricted. Raw PV production and on-site solar use remain intact. After eligibility, valid tariff intent can inform future projections when timing is the only blocker; pending restoration keeps authority. Pending writes, stale readback and other execution blockers do not establish a confirmed hold or authorize future tariff-control assumptions. These are modelled projections, not measured power or realized savings.

Export Limit diagnostics and next actions expose `export_limit_change_rate_limited`, `next_eligible_change_at`, `last_dispatch_reserved_at` and `last_change_observed_at`. Calendar entries remain planned previews and are labelled deferred while the ceiling applies. The deadline is the earliest timing eligibility, not a promise that other blockers will clear then.

### Automatic recovery after a temporary Enphase rejection

Planner allows three recovery attempts after Enphase explicitly reports a temporary pre-write failure. After an unsuccessful check, Planner waits at least five minutes before another check and respects the recorded dispatch cooldown and any longer command interval. Planner persists each definitive rejection and its daily allowance charge together. If the process stops during dispatch, the recovered uncertain request charges the allowance once. Retry counts, deadlines and operator-required pauses survive unrelated reloads and subsequent startup recovery for the same enabled export target. Authorized startup recovery can run the read-only installer check after Home Assistant starts and startup grace completes. Both ordinary export control and recovery writes wait for final startup activation preflight. Planner persists the provisional gate with arming. Restart and device-only configuration changes resume from disarmed recovery until final validation or an operator arm. A startup retry takes a fresh installer snapshot using the same attempt. Feedback events and planner refreshes share one wakeup. Installer checks run outside the planner and command locks. Before dispatch, an operator pause, a pending gateway request, a runtime replacement or a changed tariff can defer recovery without consuming the affected attempt. If Enphase is already handling another request, Planner defers the retry without charging a write.

Turning off Automatic Control revokes retry authority before startup cleanup. A retry at the final write guard gives back its attempt and reservation if the write has yet to start.

Enphase Energy v5.2.5b2 chains the underlying timeout, disconnect or HTTP 502, 503 or 504 to the pre-write service rejection. Automatic retry also requires an Enphase version that exposes the guarded apply hook. The installer preparation hook checks the activation session, gateway settings and installer form. Guarded apply compares the prepared snapshot under the Enphase write lock, then rechecks Planner authority and current tariff after Enphase has saved its pending intent and acquired the HTTP connection, immediately before sending the PUT headers. If authority is withdrawn, the tariff changes or a timeout occurs before dispatch, Enphase clears any unsent intent and Planner releases the dispatch reservation without spending the retry, daily allowance or cooldown. A timeout after dispatch keeps the request pending for reconciliation. Deferring a startup-ready retry preserves its already-counted check. Enphase versions without guarded apply and older saved rejections without a retry episode require manual recovery.

An interrupted provisional startup arm is disarmed before the first refresh on restart. Operator disarm revokes write authority and saves cancellation with the disarm before waiting for the command lock or the startup task to finish. Startup recovery rechecks authority after validation and restoration before updating progress or arming. Startup reconciliation also commits the disarm with its recovery handoff, so another interruption preserves the intended state. Device-only option changes save the recovery handoff before disarming, so startup can resume validation even if restoration or replanning was interrupted. Failed probes use the installer error even if Enphase publishes unavailable settings during the check. Definitive installer or gateway validation failures during guarded apply require operator intervention. The final guard also checks that gateway readback still matches the prepared settings and the previous cooldown has elapsed. Planner rolls back the cooldown reservation and refunds a denied write's retry attempt in one Store save. An Enphase replacement runtime waits for the retiring write before it loads pending intent, and retries failed cleanup before using the Store. It requires acknowledged atomic Store writes and drains cancelled saves before releasing the shared lock. Planner defers recovery during an Enphase entry reload without spending a readiness check. Definitive Enphase rejections remain visible if cleanup fails or its deadline expires. A cancelled readiness claim or unsent write reservation is rolled back on disk even while a refresh has a save batch open. Planner also rolls back a cancelled reservation in one save and starts the rolling allowance at guarded send time when that timestamp is available.

If startup activation fails, or the production evidence contract changes, Planner keeps Export Limit ownership only for a resumable retry on the same mapped gateway. Other ownership enters the normal restoration path, including its cooldown and readback requirements.

An operator disarm supersedes an in-progress option handoff. Planner still attempts Export Limit restoration after a transient disarm save failure. If Planner restarts after the disarm is saved, it resumes restoration of any retained baseline using the normal reservation and readback checks. A device-only options change preserves a recovery that was already disarmed through cancellation, restoration, and replanning. A temporary installer rejection during guarded apply spends a readiness check even when no request was sent. The unsent request leaves the daily allowance and dispatch cooldown available.

Compatible Enphase releases publish an opaque gateway identity with settled feedback and return it with the installer snapshot. Planner binds its retry and restoration baseline to that identity. A gateway replacement can keep the same site, entity, watts and slew rate. Planner checks the identity before crediting a retry or restoration, including after saving a sensor or Select alias. Enphase corroborates settings against the current gateway inventory before accepting an identity-bound write, even when the settings endpoint returns a single row. A provider-confirmed pre-write settings change rolls back the reservation and leaves the daily allowance available.

If fresh, settled feedback for the same registered control identifies a replacement for a pending request, explicitly resuming Export Limit retires the request and its baseline. A legacy pending request without a saved identity first has to reach the unconfirmed timeout when the companion starts publishing identity. In both cases, Planner retains the dispatch reservation and attempt accounting and records the uncertainty without crediting confirmation. Upstream pending intent still blocks retirement. Settled ownership retirement also requires feedback from the same registered control. A legacy retry or settled baseline without an identity requires explicit resume once the companion starts publishing it.

After the check, Planner reads the current tariff and fresh, settled settings from the same control. If the setting already matches the current tariff, Planner clears the retry without a device command. This also applies if the tariff changes while startup recovery is waiting to arm. An external setting change retires the old restoration baseline and preserves the retry budget. A temporary rejection after startup re-arms preserves the remaining checks and schedules a new deadline. The usual production gate, operator pause, per-device switch, daily action cap, durable reservation and matching gateway confirmation still apply. If fresh evidence shows a write is needed and the daily cap is reached, the next check waits for the allowance to reopen. If the cap closes during the check, that deferral preserves the check for when the allowance reopens. An uncertain write stays pending for reconciliation. Restoration stops the automatic checks and keeps the retry details while restoration is unresolved. After automatic control stops, fresh readback that already matches the baseline can settle restoration without a write. Timed operator pauses defer checks until the pause expires.

The Export Limit status includes the retry state, reason, attempts used, maximum attempts and next check time. For exhaustion, ambiguous rejections, unsupported topology, disabled upstream controls or expired or denied installer access, resolve the cause in Enphase Configure and use `ha_energy_planner.resume_control` for `enphase_export_limit`. A pending write continues to require settled gateway feedback before it can be resumed.

Old cooldown records without confirmation timing, present-but-null legacy timestamps and malformed/future timestamps start a conservative, persisted five-minute wait. Backward wall-clock movement re-anchors the retry deadline and cooldown while retaining the consumed retry budget. It also keeps the delay after a storage error bounded. Future-dated export attempts count against the rolling daily allowance for up to 24 hours from the correction. Planner persists the corrected accounting time and preserves the original execution audit. Unresolved commands remain blockers independently of clock repair. Repair preserves the original restoration audit identity, so replay after a crash and clock adjustment cannot create another confirmed calendar action for the same request.

Deterministic tests cover these timing and recovery contracts. No live Home Assistant access, physical-device timing validation or deployment is part of this change.
