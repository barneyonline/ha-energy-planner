## Migration-repair test uses the exported accessor

The original test indexed `hass.data["repairs"]["flow_manager"]`. On
2026.12.0b2 that value is a `RepairsData` object, which raised `TypeError`
before the test could open the flow. The test now calls
`repairs_flow_manager(hass)`, which both the 2026.11.0 minimum and the beta
export. The test opens the repair, migrates the entry to version 5, loads it
and verifies that Core clears the issue. Planner's production repair uses
the `RepairsFlow` interface.

## HVAC and Recorder

### Daikin Infrared can report the state it requested

Core's new `daikin_infrared` climate entity marks its state as assumed. A
successful infrared transmission immediately updates its cached mode and
setpoint. The optional receiver decodes the physical remote's commands. Both
paths reflect a command, so a blocked emitter can leave Home Assistant showing
the requested state while the appliance stays in its previous state.
[Tagged IR climate entity](https://github.com/home-assistant/core/blob/2026.12.0b2/homeassistant/components/daikin_infrared/climate.py#L215-L228) ·
[Tagged transmit path](https://github.com/home-assistant/core/blob/2026.12.0b2/homeassistant/components/daikin_infrared/climate.py#L382-L391) ·
[Daikin Infrared documentation](https://rc.home-assistant.io/integrations/daikin_infrared#known-limitations)

The original HVAC checks accepted a mapped climate entity based on its
state and capabilities. Its adapter uses Home Assistant state to confirm
writes and restore baselines. An IR entity can meet these checks with its own
cached state. On the beta, a synthetic `climate` state with
`assumed_state: true` passed both Planner's capability check and the
mode-and-setpoint confirmation predicate. A Docker probe using Core's actual
Daikin Infrared entity and a mock transmitter reproduced the same result
through Planner's confirmation method. The follow-up rejects assumed state
at capability discovery, before dispatch, and when confirming takeover or
restoration. If feedback becomes assumed during an owned session, Planner
keeps outstanding restoration settings and forces a health refresh. An
assumed report cannot settle an HVAC cycle, corroborate a zone change, prove
that a damper stayed closed, establish an HVAC calendar start, or qualify an
operating interval for thermal learning. If a matching mode was assumed, the
rest interval starts when observed feedback arrives. A fresh
user command still takes priority when Home Assistant shows its requested
setting as assumed. Recovery carrying the same context keeps that override.
An observed head-only shutdown can proceed while an unused zone reports assumed
state. During an away hold, that unowned zone cannot trigger a restore that
restarts the head.
AirBase restoration can retry when assumed feedback prevents every physical
write. AirBase zone restoration rechecks the head at dispatch to avoid
waking it after a manual shutdown.
A repeat of the Docker probe confirmed that Planner refused acquisition,
declined confirmation and retained the baseline for restoration without
transmitting a Planner command.
The AirBase safe Off start requires the specific LAN Daikin provider and
matched registry identities.

### LAN Daikin readback still has the expected interfaces

Core moves from `pydaikin==2.22.1` to `2.24.1` and wraps Daikin command failures
in a translated `HomeAssistantError`. The beta still puts the coordinator on
`entry.runtime_data`, exposes `coordinator.device`, and keeps the native AirBase
zone switch and climate unique ID patterns used by Planner. AirBase still
inherits `update_status(..., force_refresh=True)`. The argument bypasses the
TTL for dynamic resources, while the driver can reuse cached model information.
Planner already handles service errors through its command recovery path. The
source checks support retaining the LAN adapter. A device check should exercise
Off/Dry acquisition and restoration, plus what happens when a command times out
or readback fails.

### Custom Recorder URLs may open a different database

The beta pins SQLAlchemy `2.1.9`. The updated URL parser decodes percent escapes
in a custom Recorder database name or SQLite path. If the previously used name
contains a literal percent escape such as `%20`, encode the percent as `%25`
(for example `%2520`) to continue addressing that database. This does not affect
default Recorder storage. The official Docker images reproduced the parse
change. SQLAlchemy 2.0.54 in Core 2026.11.0 resolved `ha%20db` literally.
SQLAlchemy 2.1.9 in 2026.12.0b2 resolved it to `ha db` and required
`ha%2520db` for the literal name. An installation that opens an empty
database may lose access to the raw history Planner needs for learned
household load and EV charging calibration. Check that Recorder still returns
pre-upgrade data for the mapped load, charging and SoC entities. In a synthetic
upgrade, Planner read all six saved rows from 2026.11.0 with the corrected URL
on 2026.12.0b2. The uncorrected URL opened a new SQLite database and returned
zero rows. The tagged `state_changes_during_period` interface still accepts
the arguments Planner uses.

## Mapped devices and optional improvements

- **Energy dashboard battery telemetry.** Core supports per-direction battery
  energy and power and can read a battery-capacity sensor. These are dashboard
  preferences. Planner reads its explicitly mapped telemetry and its own
  configured usable capacity. Keep the Planner mappings independent. Use the
  dashboard's directional measurements for comparison where the hardware
  reports them. A separate opt-in usable-capacity entity could support batteries
  whose capacity changes, with kWh conversion, freshness and plausible bounds
  checked before using the value in a plan.
